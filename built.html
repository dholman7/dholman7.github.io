How this was built

Claude Code wrote nearly all of the code in these six repositories, and every commit says so in a Co-Authored-By trailer. This page covers my part: the decisions, the gates every change had to pass, and five times something was wrong and how it got caught.

The working method

  • I set what each project had to prove and the rules it couldn't break. The main one: no test is ever made to pass by weakening an assertion. A green test that hides a bug is worse than a red one.
  • Every external write waited for my approval. That covered every push, repository, Jira change, and PR comment. Each one was shown to me as an exact target and an exact change first.
  • Measurement came before claims. Agents are scored against bugs seeded into the app, on tasks split into a tuning set and a held-out set. Cheap Haiku 5.5 runs were used for iteration; Opus 5.5 runs for numbers that get published.
  • Reviewing and reporting were separate steps. Findings, including the agent's own, were re-checked against the code before anyone acted on them.

The published benchmark runs billed to the API cost $5.04 in total. When the API credits ran out, the next 4 published runs (the v3 blind held-out set) and the prompt-injection red teams went through headless Claude Code on a Claude subscription instead, with the API key stripped from its environment.

Five things that were wrong

The agent was right and the spec was wrong

What happened
On task REV-03, Storywright kept reporting an app defect instead of producing a passing test. The scenario said a low-confidence extraction has confidence 0.40, but the app correctly produces 0.30.
How it was caught
The benchmark records each trial's diagnosis. Reading the failed trials showed the agent's diagnosis was correct and the Gherkin was not.
What changed
The scenario was fixed in the app. The benchmark wasn't edited in place: v1 stays frozen with the defect documented, and v2 carries the fix, so old results stay comparable.

The first diagnosis was wrong

What happened
A UI benchmark task (UI-03) passed locally but failed validation in CI. The first explanation, concurrent SQLite writes during setup, was plausible. A fix for it was committed, and CI still failed.
How it was caught
The fix also made validation print the first failure. The real cause was the Next.js dev-tools button, which is also named "Next" and collided with the pager's "Next" button.
What changed
A new rule, PW-14 (match control names exactly), enforced by lint in the app, the shared Playwright skill, and Storywright's prompt, so the whole class of bug can't come back.

A shortcut corrupted the harness

What happened
To save time, each agent's private copy of the app shared the base Python environment through a symlink. Running a tool inside a copy quietly re-pointed the base environment's install at that copy.
How it was caught
The base environment was found pointing at a deleted directory. Sequential runs had only worked because scoring re-synced it, and parallel trials would have run each other's code.
What changed
Every copy now builds its own environment from uv's cache, in both the benchmark and review-loop's eval.

A prompt rewrite lost a rule

What happened
Storywright v0.3 moved one rule out of its prompt and into the target repo's test guide (AGENTS.md): a failed status assertion must show the response body. The benchmark's target commit predates that guide, so the rule disappeared there. On a 422, the model then blamed the app for its own mistake, and held-out success fell from 58/60 to 55/60.
How it was caught
The drop showed up in the next held-out run, where all three new failures carried the same false "app defect" diagnosis.
What changed
The prompt states the rule again for every repo, and a regression test pins it. Because a held-out result triggered this fix, the held-out scores aren't blind, which is why the landing page says so.

98fa237

The dashboard headline showed the wrong agent

What happened
The dashboard's top line read "50% of bugs caught". That was the one-call Opus baseline, not Storywright.
How it was caught
I noticed it reading the live dashboard as a visitor would.
What changed
The overview now groups runs into the agent, its baselines, and anchors. The headline compares the agent with a baseline on the same model, and every title names the benchmark version.

The reviewer, reviewed

review-loop was tried on the first four real agent-written pull requests, without posting, before it was trusted with anything. Every comment was then checked by hand against the code. On Haiku 5.5 it made five comments, and one held up. On Opus 5.5 it made two, and both held up. Those two were applied in PR #5, and the GitHub Action now defaults to Opus. Neither model posted anything a person hadn't approved.
